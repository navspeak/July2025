Key fact:
• L1 and L2 caches belong to a *core*
• Threads running on the same core SHARE these caches
==============================================
1️⃣ What is Cache Thrashing (in simple points)
==============================================

Each CPU core has small, fast caches (L1, L2). Threads rely on these caches to be fast
When too many threads run on the same core:
    - Each thread loads its own data into cache -> That data kicks out the previous thread’s data
    - When a thread runs again -> Its data is gone -> CPU must fetch from L3 or RAM (slow)
👉 This constant evict → reload → evict cycle is cache thrashing
* CPU is busy waiting on memory. Not doing useful work. More threads = worse performance
* Latency becomes unpredictable.
* You can have low CPU usage and still be slow
* get from lscpu:
    CPU(s) = x = 16
    Thread(s) per core = y = 2
    ---------
    real cores = x / y = 8

If your app has:
    Executor threads > real cores
    Netty event loops = logical CPUs
    Kafka consumers × threads > real cores
    ⚠️ High risk of cache thrashing

How to FIX cache thrashing (practical)
===================
Fix 1: Reduce thread count (most effective) Size CPU-bound thread pools to number of real cores. Not logical CPUs.
Fix 2: Tell JVM the real CPU count.In containers: -XX:ActiveProcessorCount=2.Prevents JVM from creating too many threads.
Fix 3: Separate CPU-bound and IO-bound threads CPU-bound → limited threads.IO-bound → more threads allowed. This avoids CPU cache contention.
Fix 4: Avoid false sharing (advanced)
    - Don’t share hot variables between threads
    - Pad frequently updated fields
    - Use thread-local data where possible
(This reduces cache line bouncing.)

Cache thrashing occurs when more threads than CPU cores compete for small per-core caches, causing constant cache eviction and memory stalls;
lscpu helps by revealing real core count so thread pools can be sized correctly.

-------------------------------------------------------------------------------
False sharing happens when multiple threads update different variables that happen to live on the same CPU cache line,
causing unnecessary cache invalidations and slowing the program down — even though the variables are not logically shared.

Who should care?
    Framework / library / JVM developers / Low-latency, CPU-bound systems (Netty, Kafka, trading, metrics)
    Very high-throughput counters or tight loops
    Most application developers do not need to worry about it.

What should be done?
Application developers:
    Use high-level tools (LongAdder, avoid shared mutable state, size thread pools correctly).
Library / systems developers:
    Control memory layout (padding, @Contended) where proven necessary.
