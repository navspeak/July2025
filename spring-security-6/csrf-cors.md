## CSRF
```bash
# GET Works
http -a user:ff0dca13-3534-4570-9242-9e6741c04ef8 GET http://localhost:8080/product
# POST 401 = WHY?
http -a user:ff0dca13-3534-4570-9242-9e6741c04ef8 POST http://localhost:8080/product \
   Accept:application/json \
   productId:=3 \
   productName="iPad" \
   price:=1500
```
1. Assume: CSRF is disabled (whatever it is!)
   - Spring Security still uses Session (JSESSIONID)
   - User is authenticated (Basic / Form login)
   - You login. Browser has `Cookie: JSESSIONID=abc123`. You submit POST /product. Controller adds it. => __all good?__
     - While logged in the browser, you visit a malicious site that posts a vicious product:
       ```html
       <form action="http://localhost:8080/product" method="POST">
         <input name="productId" value="999">
         <input name="productName" value="HackedProduct">
         <input name="price" value="0">
       </form>
  
       <script>
         document.forms[0].submit();
       </script>
       ```
2. Your browser has the cookie, so it attaches to the request. You app is deceieved into thinking it's from an authenticated user. And BOOM you got scammed!!!!
3. So, spring security out of box has `CSRF protection ENABLED by default`
4. **What Spring Security does OUT OF THE BOX**
   - On login / first request -> Spring generates a CSRF token -> Stores it in HTTP session
   - On every state-changing request (POST, PUT, DELETE):
     - Spring expects a CSRF token in header or request param.
     - CsrfFilter checks: `request token == session token ?`
     - If token is missing or invalid -> reject request
5. Replay the attack WITH CSRF enabled.Malicious site submits `<form action="http://localhost:8080/product" method="POST">`.
   - Browser sends `Cookie: JSESSIONID=abc123`. 
   - But attacker can't read & inject into requests (because of `Same-orgin-policy` enforced by browsers)
   - So Spring says `403 Forbidden - Invalid CSRF token`
6. When developers disable CSRF
    - In stateless APIs: No sessions, No cookies, Auth via headers (JWT / Bearer token)
    ```
    http
    .csrf(csrf -> csrf.disable())
    .sessionManagement(sm -> sm.sessionCreationPolicy(STATELESS));
    ```
    - Now: browser can’t auto-attach auth -> attacker can’t forge headers -> CSRF risk disappears

## Why an attacker cannot read your CSRF token
> Because of the Same-Origin Policy (SOP) enforced by browsers 

1️⃣ Where the CSRF token lives 
1. By default (Spring Security) CSRF token is:
   1. generated by the server
   2. stored on the server side (HTTP session)
2. A copy is sent to the legitimate browser page so it can echo it back
3. The attacker never gets server access, only browser access.

2️⃣ Same-Origin Policy (this is the wall)
- JavaScript running on evil.com
- ❌ cannot read data from localhost:8080
-  “Origin” = scheme + host + port

| Site                                           | Origin         |
| ---------------------------------------------- | -------------- |
| [http://localhost:8080](http://localhost:8080) | localhost:8080 |
| [http://evil.com](http://evil.com)             | evil.com       |
- [x] Different origins → no access

3️⃣ What the attacker CAN do vs CANNOT do
✅ Attacker CAN
- [x] Make the browser send a request
- [x] Rely on browser auto-attaching cookies
❌ Attacker CANNOT
- [] Read cookies (HttpOnly)
- [] Read CSRF token
- [] Read response body
- [] Inject custom headers (like X-CSRF-TOKEN)

4️⃣ CSRF token generation (server-side)
- Spring Security creates a token `X-CSRF-TOKEN = a8f9c3b2-1d2e-4b3c-9a2d`
- stores in it session: `Session (JSESSIONID=abc123):  CSRF_TOKEN = a8f9c3b2-1d2e-4b3c-9a2d`
5️⃣ How the token reaches the browser (legit app)
1. Option A — HTML form (classic Spring MVC)
```html
<form action="/product" method="POST">
   <input type="hidden" name="_csrf"
   value="a8f9c3b2-1d2e-4b3c-9a2d"/>

  <input name="productId" value="3"/>
  <button>Submit</button>
</form>
```
Browser submits:
```html
POST /product
Cookie: JSESSIONID=abc123

_csrf=a8f9c3b2-1d2e-4b3c-9a2d
productId=3
```
2. Option B — JavaScript / SPA (very common)
- Server exposes token only to same-origin JS:
```html
<meta name="_csrf" content="a8f9c3b2-1d2e-4b3c-9a2d">
```
- JS reads it as:
```html
const token = document.querySelector('meta[name="_csrf"]').content;

fetch("/product", {
  method: "POST",
  headers: {
    "X-CSRF-TOKEN": token,
    "Content-Type": "application/json"
  },
  body: JSON.stringify({ productId: 3 })
});

```
- Request Sent
```html
POST /product
Cookie: JSESSIONID=abc123
X-CSRF-TOKEN: a8f9c3b2-1d2e-4b3c-9a2d
```

7️⃣ Why the attacker cannot do the same
- Malicious site tries this:
```html
fetch("http://localhost:8080/product", {
method: "POST",
headers: {
"X-CSRF-TOKEN": "???"
}
});
```

Problems:
- ❌ Cannot read your page’s <meta> tag (different origin)
- ❌ Cannot read cookies (HttpOnly)
- ❌ Cannot guess CSRF token (random, per session)
- ❌ Browser blocks reading response anyway

- So the attacker can send a POST…but cannot make it valid.

8️⃣ Why cookies alone are not enough
- Browser always does this automatically: `Cookie: JSESSIONID=abc123`
- That’s why CSRF exists.
- CSRF token proves:`This request was created by JavaScript / HTML that came from my site.`

9️⃣ Final mental model (remember this)
- Cookies → who you are
- CSRF token → where the request came from

🔟 Interview-grade one-liner
- An attacker can trigger a request, but cannot read the CSRF token because browsers enforce same-origin policy. 
- Since the token is only accessible to pages from the same origin, forged cross-site requests fail CSRF validation.
